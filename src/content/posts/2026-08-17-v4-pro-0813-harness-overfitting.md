DeepSeek V4-Pro-0813 正式发布以后，一个很有意思的说法开始在社区里反复出现：V4-Pro 的 Agent 能力虽然很强，但似乎非常依赖 Harness。换到 DeepSeek 自己的 Harness 或某些它比较熟悉的 Agent 框架里表现很好，一旦换到另一套工具定义、调用方式或者工作流，能力就可能明显下降。

于是有人开始用一个更直接的词来描述这种现象：**Harness 过拟合**。

这个说法乍一看很像社区在模型表现不符合预期以后找出的新解释，但它并不是完全没有依据。更准确地说，目前已经有一些现象支持“V4-Pro 对 Agent 运行环境比较敏感”，也有研究证明大规模 Agent trajectory 训练确实可能导致模型学习工具接口本身的捷径。不过截至目前，还没有足够的独立实验能够证明 V4-Pro-0813 已经严重过拟合 DeepSeek 官方 Harness。

因此，与其直接下结论，不如先弄清楚这里所谓的“过拟合”究竟指什么。

## 社区为什么会怀疑 V4-Pro 对 Harness 过拟合

这个问题实际上并不是 0813 正式版发布以后才出现的。

在更早的 V4-Pro 测试中，就已经有人发现一个比较反常的现象：模型在普通一次性编程任务中的表现很强，但进入自定义 Agent Harness 后，表现反而会明显下降。

Gert Labs 此前测试 V4-Pro 时就遇到过这种情况。他们的结果里，V4-Pro 在 one-shot coding 任务上明显强于 Flash，但到了自制的 agentic harness 中，Flash 反而表现得更稳定。测试过程中还出现了工具调用格式、JSON 输出以及 Agent 迭代流程方面的问题。

他们因此提出了一种可能性：V4-Pro 可能对常见 Harness 和 Agent 的迭代方式存在比较强的适应，而在没有见过的运行环境中，泛化能力没有预想中那么好。

中文社区里也能找到类似的体验。有人给 V4-Pro 配上自己长期使用的 Agent 工作流后，发现模型会随机漏掉部分约束；也有人认为同一个 Harness 在 Codex 等模型上运行正常，换成 V4-Pro 后却需要重新调整提示词、工具说明和执行流程。

但问题在于，社区中同时也存在完全相反的案例。

另一些用户自己搭建了更加完整的 Harness 后，V4-Pro 的表现反而明显提高。在复杂工程任务里，它能够持续执行数小时，并且表现出比裸模型调用明显更强的任务推进能力。也就是说，目前看到的现象并不是“V4-Pro 不适合 Harness”，而更像是：

**V4-Pro 的 Agent 表现对 Harness 的设计特别敏感。**

这两句话看起来很接近，实际含义却完全不同。

前者意味着模型本身的 Agent 能力存在缺陷；后者则意味着模型的能力很强，但能否释放出来取决于运行环境，而这种依赖程度可能比其他前沿模型更加明显。

## 什么才算真正的 Harness 过拟合

Agent 模型经过大量后训练以后，对特定 Harness 形成偏好，在技术上完全可能发生。

传统语言模型训练主要面对文本，而现在越来越多的 Agent 后训练数据已经变成完整 trajectory。一条训练轨迹里不仅包括模型的推理和回答，还会反复出现工具名称、参数结构、工具返回结果以及固定的执行顺序。

例如，一个模型在训练过程中可能大量看到这样的模式：

```md
read_file(path)
bash(command)
apply_patch(patch)
```

理想情况下，它应该学会的是背后的抽象能力：

```md
需要读取文件
→ 找到具有文件读取能力的工具
→ 根据 schema 调用
→ 根据结果继续执行
```

但如果训练环境长期保持相似，模型也可能学到另一种更简单的规律：

```md
遇到代码任务
→ read_file
→ bash
→ apply_patch
→ bash test
```

两种策略在原始 Harness 中看起来几乎没有区别，直到把工具改名。

假如完全保持任务、工具能力和执行环境不变，只把：

```text
read_file
```

改成：

```text
inspect_file
```

把：

```text
bash
```

改成：

```text
terminal_exec
```

模型的成功率就突然大幅下降，那才真正接近所谓的 Harness 过拟合。

相关 Agent 研究已经观察到这种现象。有研究将它称为 **interface shortcutting**：经过大量 Agent trajectory 训练以后，模型有时会把工具接口本身当成完成任务的捷径，而没有完全学习接口背后的语义。

甚至会出现一种很典型的错误：测试环境已经不存在训练时使用的工具，模型仍然试图调用旧工具名称。

从这个角度看，“Agent 后训练越重，模型就一定越通用”其实并不成立。后训练能够显著提高模型在复杂任务中的执行能力，但如果训练环境缺乏足够的多样性，也可能同时增强模型对某些固定接口和工作流的依赖。

## 但 V4-Pro 的很多问题可能只是协议兼容

这里又必须给“过拟合论”降一点温。

V4-Pro 本身的工具调用协议并不是最普通的 OpenAI-style function calling，在社区适配过程中，已经有人遇到过 DSML tool-call markup、reasoning state 保留以及多轮工具调用状态处理方面的问题，这些都会让不同 Harness 之间的表现差异被进一步放大。

因此很容易出现一种误判：模型在某个环境里“看起来不会用工具”，但实际上它可能已经正确生成了工具调用指令，例如：

```text
调用 bash
```

在 DeepSeek 官方 Harness 中，这类输出会被正确解析并执行，于是用户看到的是完整的工具调用流程正常运行。

但如果换到第三方 Harness，而 adapter 没有完整实现相同的协议解析逻辑，这段内容就可能被当作普通 assistant 文本直接展示出来，结果在用户视角就变成：

```text
V4-Pro 不会调用工具。
```

从体验上看，这种情况确实很容易被归因成“模型换环境就变笨”，也因此和所谓 Harness 过拟合现象非常相似，但在技术层面，两者其实是完全不同的问题。

前者更接近模型泛化或接口适配问题，即模型生成了正确的工具调用，但没有被正确理解或执行；后者则是基础设施层面的兼容问题，本质是：

```text
模型理解了工具接口，但 Harness 没有正确解析或还原执行语义
```

如果不把这两类情况区分开，就很容易把所有“换 Harness 表现下降”的现象统一归因到模型本身的过拟合上。

因此，仅凭“在 DeepSeek 官方 Harness 里表现很好，但在 OpenCode 或其他框架里表现一般”这一类体验，还不足以作为任何确定性结论的依据。

## Pro 比 Flash 更容易出现这种争议，反而比较值得注意

目前让我觉得最值得继续观察的一点，是一些早期测试中 Pro 和 Flash 的差异。

按正常直觉，更大的 Pro 模型拥有更强的推理和理解能力，面对一个陌生工具接口时，理论上应该比 Flash 更容易适应。但部分测试却出现了相反结果：

```text
one-shot coding：
Pro > Flash

自定义 Agent Harness：
Flash > Pro
```

如果这种现象能够在 V4-Pro-0813 上被稳定复现，就很值得研究。

一种可能的解释是，Pro 接受了比 Flash 更重的 Agent 后训练。在后训练过程中，它不仅学到了更强的长程任务执行能力，也形成了更强的 interface prior，即对某些工具形态、执行节奏和 Agent 工作流拥有更明确的先验。

在熟悉环境中，这些先验是优势。模型不用重新摸索如何工作，可以迅速进入已经训练成熟的执行模式，到了陌生环境里，同样的先验却可能变成负担。

这并不意味着模型“被训坏了”，而更像是后训练带来的能力与偏好同时增加。模型越来越像一个训练成熟的 Agent，而不再只是一个拿到任意工具说明以后从零开始理解环境的通用语言模型。

这也是“过拟合”这个词容易产生误导的地方。

## 后训练 Scaling 可能不是没有代价的

GLM-5.3 的发布恰好让这个问题变得更有意思。

智谱这次非常强调后训练 Scaling：在完全相同的基座上，通过更多长程环境、更丰富的任务以及更长时间的强化学习，把 GLM-5.2 明显推到了新的能力水平。这个结果证明，强大的 base 在预训练完成以后仍然可以继续开发，Agent 能力也确实能够通过大量环境训练被明显增强。

但另一面的研究正在提醒我们：如果 Agent 后训练越来越重，训练环境本身也必须跟着变得更加多样。

否则可能出现这样的结果：

```text
Agent benchmark        ↑↑
熟悉 Harness           ↑↑
陌生 Harness 泛化能力    →
甚至                    ↓
```

模型越来越擅长完成训练环境中的复杂任务，却不一定同比例提高对陌生环境的适应能力。

这并不是后训练 Scaling 的反例，而可能恰恰是它进入下一阶段以后必须解决的问题。

过去大家讨论预训练数据多样性，现在 Agent 模型可能还需要讨论另一个概念：**Harness diversity**。

工具叫什么、参数怎么组织、错误如何返回、文件编辑是什么接口、Shell 如何执行、任务状态怎样维护，这些看起来只是工程细节，但一旦它们进入数以百万计的训练 trajectory，就可能成为模型学习内容的一部分。

## 目前还不能把这个结论直接套到 0813 上

截至目前，我认为把 V4-Pro-0813 直接描述成“对 DeepSeek Harness 过拟合”还是太早。

目前比较明确的社区讨论，很大一部分实际上来自此前的 V4-Pro，而 0813 正式版发布的时间还很短。真正针对同一任务、同一工具能力、不同接口表示进行严格控制变量测试的数据仍然很少。

另外，V4-Pro 过去也并不是只能在 DeepSeek 自己的环境里工作。OpenHands、ResearchHarness 等其他 Agent 系统中都出现过有效测试结果。因此，“V4-Pro 离开官方 Harness 就完全不会工作”这种最极端的说法，目前显然站不住脚。

现在比较合理的判断应该是：

**V4-Pro 已经出现了一些符合 Harness sensitivity 的现象，其中部分表现也符合 Agent interface overfitting 的理论预期，但目前还无法排除协议兼容、第三方 adapter、提示词设计以及 Harness 本身质量等因素。**

这是一条值得验证的假说，而不是已经成立的结论。

## 真正验证这个问题并不复杂

如果以后有人愿意认真测试 V4-Pro-0813，其实不需要再造一个大型 benchmark。

准备一组二三十个需要文件操作、Shell、代码修改和测试的 Agent 任务，然后制作两套能力完全相同的 Harness 就足够了。

第一套使用模型熟悉的工具形式，例如：

```text
bash
read_file
apply_patch
```

第二套只修改接口：

```text
terminal_exec
inspect_file
modify_text
```

底层执行的仍然是同一套函数，任务、模型参数、token budget、reasoning effort 和运行环境全部保持一致。

除此之外，还可以进一步改变参数名称，例如：

```json
{"path": "src/index.ts"}
```

改成：

```json
{"file_path": "src/index.ts"}
```

然后比较 V4-Pro-0813、Flash-0731 和其他前沿模型的成功率，同时记录错误工具调用、旧工具名称调用、schema 错误，以及在工具失败后的恢复能力。

如果最后得到类似这样的结果：

```text
                 原始接口    扰动接口

V4-Pro-0813        88%       57%
Flash-0731         80%       74%
其他模型            86%       81%
```

那么“V4-Pro 存在明显 Harness 过拟合”才真正有了很强的证据。

如果工具改名以后性能基本保持不变，那么现在社区里很多所谓的“过拟合”，很可能只是把模型协议兼容、第三方 Harness 设计和使用体验混在了一起。

## 我更倾向于把它理解成 Harness 敏感性

目前我并不认为 V4-Pro-0813 已经可以被简单贴上“过拟合”标签。

更可能的情况是，DeepSeek 在 Agent 后训练上走得比较深，因此模型形成了非常成熟的工具使用与任务推进模式。这种训练显著提高了它在合适 Harness 中的能力上限，同时也可能让它比一些模型更加依赖环境设计。

换句话说，后训练给了它能力，也给了它偏好。

这也能部分解释 V4-Pro 发布后一个一直比较奇怪的现象：DeepSeek 官方公布的 Agent benchmark 很强，但第三方综合评测以及部分社区用户的提升体感，并没有始终呈现同样夸张的幅度。

两者之间的差异不一定意味着官方 benchmark 有问题，也不一定意味着第三方评测测错了模型。另一种可能是，到了这一代 Agent 模型以后，所谓“模型能力”已经越来越难脱离运行它的 Harness 单独讨论。

如果这个判断最终成立，那么评价未来的 Agent 模型时，除了模型本身和 benchmark，也许还应该多问一个问题：

**它是在某一套 Agent 环境里特别强，还是换一套完全陌生的工具以后仍然能够保持同样的能力？**

后者可能才是真正意义上的 Agent 泛化能力。
